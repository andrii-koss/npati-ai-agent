## 2. Резюме

1. **Домінанта часу — модель, але не завжди.** Для 127 завершених ранів із ≥3 ходами медіана wall 79.0 с, з них модель 26.7 с (**43.4%**). Для створення сайту (n=55) середнє wall 170.6 с, модель 58.5 с (34%), **верифікація 32.7 с (19%)**, читання 19.1 с (11%), редагування 12.9 с (8%), shell 2.8 с (2%), **неатрибутовано 44.7 с (26%)**.
2. **Найбільший інструментальний витрата — `code.verify.run`:** 532 виклики, p50 **26.9 с**, p90 62.6 с на виклик. 29 ранів верифікуються ≥2 разів (до 8), і тоді верифікація з'їдає **25–57%** усього часу рану (максимум виміряно: 233 с із 469 с).
3. **`changedOnly` не працює:** верифікація завжди запускає повну команду проєкту, незалежно від змінених файлів (підтверджено і кодом, і тим, що час не корелює з розміром diff).
4. **Обрізані tool-call аргументи — найдорожчий збій.** У повністю інструментованому прогоні **8 із 18** викликів були відхилені як `partial_tool_call`; на ці 8 ходів пішло **186.3 с із 296.5 с (62.8%)**. Ймовірна причина (гіпотеза): `max_tokens` не передається провайдеру — `maxOutputTokens` є лише полем каталогу моделей.
5. **Loop detection не бачить відхилених викликів:** ті самі 8 помилок поспіль не зупинили ран. Дедуплікація/детекція працює лише для виконаних викликів.
6. **TTFT бімодальний:** медіана **1 471 мс**, але середнє 5 095 мс і p90 **24 323 мс** (n=19): 3 ходи з 19 мали 22–27 с до першого токена. Користувач при цьому не бачить нічого, бо coding-стрім не шле `delta`.
7. **Фіксований префікс запиту великий:** system prompt p50 **17 243** символи (max 28 329), tool-схеми **37 875** символів (50 інструментів; 24 771 для website-edit, 8 474 для plan). Prompt caching відсутній → префікс оплачується на кожному ході.
8. **Обов'язкова рефлексія дорога:** self-review виконувався у 106 ранах, p50 **4.8 с**, p90 19.8 с, середнє 7.8 с додаткового LLM-виклику.
9. **Approval-блоки корелюють із удвічі довшими ранами:** 156.8 с проти 73.5 с (p50), 9 проти 5 ходів; 37 запитів на `code.shell.exec` висять у статусі `pending`.
10. **HMR немає, streaming немає, prompt caching немає** — три підтверджені структурні прогалини (деталі у §7–8).

### 5.1. Пояснення до сценаріїв

**Сценарій 1 (створення).** Основна маса часу — модель (34%) і верифікація (19%), але **26% неатрибутовано**. Медіана 7 ходів; p90 — 19 ходів. Найдовший виміряний HTML/CSS-ран — 296.5 с при 19 ходах (§4). Незалежне підтвердження з `REPORT.md`: 220 148 мс для «нового порожнього HTML-шляху» і 393 с для історичного шляху з шаблоном — це **два окремі прогони**, не статистика.

**Сценарій 2 (CSS).** Найдешевший: 4 ходи, 32.7 с, верифікація **не запускається** (0 викликів) — для HTML/CSS і style-preview `verificationTools=[]`, тому `verificationDisabled` (Stage 0, `code-route-lifecycle.ts:307`, `coding-agent-review-coordinator.ts:577`). Ризик: CSS-зміна проходить без жодного білда.

**Сценарій 3 (компонент).** Проксі — редагування заголовка/H1 у Next.js, Nuxt, React, Vue, Astro, Svelte тощо. 55.9 с, 5 ходів, верифікація 12.7 с. **25 із 37 ранів** мали попередження scope-guard: змінювалися файли поза заявленим фокусом (напр. `index.html` при фокусі «HTML»). Це не блокує ран (guard — advisory, Stage 0).

**Сценарії 4–6.** У БД немає жодного рану з інтентом «виправити TS-помилку», «виправити білд» або «додати сторінку». Виправлення білда відбувається **всередині** repair-циклу (`verification_repair` — 11 подій у 8 ранах), але окремим сценарієм не зафіксоване. Тому — `Не виміряно` без екстраполяції.

**Сценарій 7 (повторне редагування).** 87 ранів, 90% успіху, wall p50 65.9 с, але p90 236.6 с — довгий хвіст. Провали: `loop_detected` 2, `provider_error` 2, `self_review_unavailable` 2, `budget_exhausted` 2, `cancelled` 1, `step_limit` 1.

## 7. Підтверджені bottlenecks

Вплив: **High** — понад 20% часу або прямий вплив на кожен ран; **Medium** — 5–20% або частина ранів; **Low** — менше 5%.

### High

**H1. Повна верифікація повторюється (build/test/typecheck).**
Доказ: 532 виклики, p50 **26 928 мс**, p90 62 598; 29 ранів із ≥2 верифікаціями (2×—20 ранів, 3×—4, 4×—2, 6–8×—3); у найгірших ранах — **233 с із 469 с (50%)**, 273 с із 1 093 с (25%), 125 с із 219 с (57%). `changedOnly:true` передається (`code-ports-wiring.ts:197`), але **ніколи не читається** в тілі (`:194-263`), тому кожен виклик — повний `npm run build`/`npm test`.
Мінімальна пропозиція: перевикористовувати результат верифікації, прив'язаний до ревізії workspace (механізм `code-workspace-revision` уже є), і не верифікувати незмінений стан.

**H2. Обрізані аргументи tool-call (`partial_tool_call`).**
Доказ: 8 із 18 викликів у трейсі (§4), 186.3 с (62.8% wall); `max_tokens` не передається — `maxOutputTokens` є лише полем каталогу (`packages/omniroute-adapter/src/types.ts:346`, `normalization.ts:381`), у тіло запиту не потрапляє (`omniroute-engine.ts:83-98`).
Мінімальна пропозиція: задати ліміт вихідних токенів для tool-викликів (або вимагати менші файли за один виклик) — це не новий механізм, а відсутній параметр наявного запиту.

**H3. Відсутність prompt caching при великому фіксованому префіксі.**
Доказ: system prompt p50 17 243 символи + tool-схеми 24 771–37 875 символів **на кожному ході**; оцінка контексту рушія — p50 **8 680** токенів/хід (p90 11 443, max 19 277; 525 виміряних ходів); медіана 7 ходів → префікс пересилається 7 разів. 0 збігів `cache_control`; хелпер стабільного префікса `systemPromptStablePrefix` існує, але не має споживача (`coding-agent-runner-prompt.ts:127`).
Мінімальна пропозиція: увімкнути провайдерський cache-control на вже наявному стабільному префіксі; окремої реалізації не потрібно.

**H4. Відсутність streaming для coding-рану.**
Доказ: `send()` не має `delta` для coding-гілки (`chat-stream-routes.ts:269`); при TTFT p90 24.3 с користувач не отримує жодного сигналу прогресу до кінця ходу.
Мінімальна пропозиція: прокинути вже наявні провайдерські delta-події (`onGenerationProgress`) у `delta`-канал; двигун уже стрімить усередині (`chat-stream.ts`), назовні віддається лише лічильник.

### Medium

**M1. Self-review як додатковий LLM-виклик на кожен ран зі змінами.**
Доказ: 96 викликів, p50 4 840 мс, p90 19 818 мс, середнє 7 828 мс; у 106 ранах `ran=true`. Мінімальна пропозиція: запускати лише коли є підстави (напр. verification failed або великий diff), а не завжди.

**M2. Approval-блоки.**
Доказ: 122 події `approval_required` у 47 ранах; у порівнянні ранів із tool-activity-блоком (36) wall p50 156.8 с проти 73.5 с, ходів 9 проти 5; 37 `pending` запитів на `code.shell.exec`. Мінімальна пропозиція: не пропонувати моделі shell-команди, які все одно вимагатимуть approval у цьому режимі (політика вже знає класифікацію).

**M3. Loop detection не покриває відхилені виклики.**
Доказ: 8 ідентичних `partial_tool_call` поспіль → ран не зупинився; `repeatedErrors` наповнюється лише у `appendToolResult` для виконаних (`:483-489`), а `normalized.rejected` обробляється окремо (`:178-213`). Мінімальна пропозиція: годувати коди відхилень у той самий детектор.

**M4. Переважно пофайлові правки замість patch.**
Доказ: 1 732 `write`/`edit` проти 165 `apply_patch`; 852 ходи з одним викликом. Мінімальна пропозиція: підсилити наявний `apply_patch` у guidance (механізм уже є і працює атомарно).

**M5. Старт рану до першого виклику моделі.**
Доказ: p90 12 991 мс, max 28 268 мс (n=179). Мінімальна пропозиція: спершу виміряти розклад усередині (git-гілка / MCP discovery / snapshot / sandbox), потім вирішувати.

### Low

**L1. Затримка відображення Activity** — полінг 3 с (UI), heartbeat 15 с. Вплив на сприйняття, не на час рану.
**L2. Дублікати читань** — p90 3 на ран; медіана 0.
**L3. Неатрибутовані 18–26%** — не сам по собі bottleneck, а відсутність інструментування (§9).

## 8. Що НЕ підтвердилося (щоб не оптимізувати зайве)

- **Фіксованої послідовності Read → Plan → Read → Edit немає** — ні в коді, ні в послідовності подій.
- **Обов'язкового делегування немає** — 0 викликів `code.agent.spawn`.
- **Обов'язкового планування в coding немає** — 21 виклик на 179 ранів.
- **Повних логів у контексті немає** — діють ліміти 30 000 символів / 2 000 рядків.
- **Зайвого перезапуску Preview немає** — але HMR теж немає (це інша проблема: відсутня можливість, а не зайва дія).
- **Паралелізм read-only не є вузьким місцем** — він майже не спрацьовує, бо провайдеру вимкнено `parallel_tool_calls`; це обмеження, а не витрата.

## 9. Не виміряно (і чому)

| Що | Причина |
|---|---|
| TTFT на всій вибірці | `model_first_token` **не персиститься** в `code_activity_events`: 0 рядків із `firstTokenMs`; є лише в одному pino-лозі (19 семплів) |
| Розклад токенів: system / tools / history / results | Провайдерський usage зберігається лише сумою (`tokenCount`); погодинного розкладу немає, токенізатора в оточенні немає → наведено **символи** та оцінку рушія |

| Повторні `npm install` | Команди не персистуються (Activity — metadata-only за дизайном) |
| Причини 8 повторів `partial_tool_call` | Немає поля «чому обрізано» (ліміт токенів / обрив стріму / розмір файлу) |

## 10. Обмеження та наступні кроки вимірювання

1. **Контрольовані запуски не виконувалися.** Локальний стек ізольований технічно, але його ізоляція від робочих даних не підтверджена документально; запуск нових write-сценаріїв створив би нові проєкти/сесії в цій БД. Тому сценарії 4–6 — `Не виміряно`, а не «виміряно на око».
2. **Вибірка неоднорідна:** 12 framework-e2e, harness-прогони (`User request:`), інтерактивні прогони і прогони з різних образів. Для чесного порівняння потрібен фільтр за версією образу (`runner_version` у replay-бандлі вже є).
3. **Щоб закрити прогалини, потрібно лише ввімкнути вже наявні джерела:**
   - персистити `model_first_token` (подія вже генерується — `coding-agent-runner.ts:507-510`, але в БД її немає);
   - писати `stage: "preview"` у durable activity (подія вже є — `code-chat-website.ts:87`, але йде лише в UI-проєкцію);
   - фіксувати `max_tokens`/`finishReason` у model-події, щоб відрізняти обрив від ліміту;
   - розділяти model-час на `main` / `self_review` (поле `modelPurpose` уже є в подіях).
4. **П'ять метрик Етапу 0 підтверджені як доступні** — усі розраховані тут із наявних таблиць, без нових механізмів.

**Зупиняюсь на Етапі 1.** Оптимізація не пропонується і не виконується; наступний етап — лише за окремою командою.
