# Npati Code — результати оптимізації швидкості та дисципліни

**Дата:** 2026-10-22. **Baseline:** `docs/audit/coding-agent-baseline.md` (образ `ed7c6d8`).
**Після:** образ `npati-measure:after-dc4596c` (усі виправлення етапу 2). Додатково виміряно `after-1369a50` — експеримент, який **відкочено** (див. нижче).
**Метод:** той самий harness (`scripts/measure-coding-scenarios.mjs`), ті самі сценарії, моделі, Company на кожен прогін, 1 прогін на сценарій. Між baseline і «після» у harness змінено лише очікування фонових run-ів (30 с тиші замість 8 с, будь-який активний run компанії) і критерій успіху S3 (вердикт кореневого run); `totalMs` рахується до кінця останнього run, тож очікування в нього не входить. Сирі дані: `artifacts/measure/{baseline,after,after2}-*.json`.

> **Обмеження інтерпретації.** Один прогін на сценарій. Різниці в межах ±20 % (особливо у часі) можуть бути розкидом моделі, а не ефектом змін. Профіль `hosted-native-tools` не виміряно (немає підключеної моделі).

## Що покращилось (лише виміряне)

1. **Успішність gemma: 3/6 → 5/6.** S5: замість 4 вгадувань типу поля (`STRING`, `TEXT`) і `loop_detected` — 5 викликів моделі й створена таблиця (помилка тепер містить перелік допустимих типів). S1: без `loop_detected` на повторних `unchanged`-правках.
2. **Зміна кольору без зайвого self-review.** deepseek S2: 5 → 4 виклики моделі (`self_review_skipped`); gemma S2: 4 → 3, 64 → 18 с.
3. **Медіана загального часу:** deepseek 98 → 71 с, gemma 59 → 45 с; deepseek S6 151 → 90 с.
4. **Без S3 менше викликів моделі і tool calls** на обох моделях (deepseek 29 → 25 / 37 → 33; gemma 31 → 27 / 31 → 30).
5. **Запит на аналіз** — 0 write в усіх 4 прогонах (як і в baseline).

## Що погіршилось і що з цим зроблено

**deepseek S3 (дизайн за фото): 392 → 634 с, 12 → 24 виклики моделі.** Ремонти зросли з 3 до 8 ходів: модель тричі за ремонт викликала `code.preview.screenshot`, а в кореневому run — `code.image.view` вже прикріпленого фото. Ймовірна причина — нове правило промпту «після зміни перевір один раз».

- Експеримент `1369a50`: не пропонувати ці два інструменти, коли правка сайту має прикріплений референс (систему однаково перевіряє Preview + скриншот), і уточнити правило. Виміряно (`after-1369a50`, S1→S3):
  - deepseek S3: **307 с, 11 викликів моделі, але `visual_acceptance_failed`**;
  - gemma S3: 483 с, 18 викликів, `visual_acceptance_failed` (як і в усіх попередніх прогонах gemma).
- Висновок: швидше, але з однією вибіркою — провал візуальної перевірки на моделі, яка до цього проходила. Оскільки стабільний «дизайн за фото» — критерій приймання, **`1369a50` відкочено** (`7c17f10`). Регресію часу S3 на deepseek прийнято свідомо до появи кращого рішення (див. наступні кроки).

## Що не вдалося виміряти

- **Профіль `hosted-native-tools`** — немає підключеної моделі.
- **Медіана з 3 прогонів** — виконано 1 прогін на сценарій (рішення про витрати).
- **Ефект компакції (F-01)** — у замірах вона майже не спрацьовувала (1 подія в baseline deepseek, 0 у «після» deepseek, 1 в after2 gemma): сценарії короткі. Ефект підтверджено лише юніт-тестом.
- **Повтор провайдера (F-11)** — жодного збою провайдера за всі прогони; живого ефекту немає.
- **`stopDetail`** не заповнюється для `visual_acceptance_failed`: цей статус виставляє приймальна перевірка після run, а не `stop()` runner-а.
- **Аналіз зовнішнього сайту**: обидві моделі відповідають звичайним чатом без завантаження сторінки (запит не потрапляє в Coding Agent). «0 write» виконано, але сам аналіз не відбувається — це маршрутизація чату, поза межами цього етапу.
- **Стрімінг tool calls і оновлення Live Preview після кожного патча** — не змінювалось і не вимірювалось: Preview запускається після run (архітектурна зміна поза мінімальним обсягом).

## Наступні 3 кроки

1. **S3 «дизайн за фото»:** зробити скриншот Preview частиною одного системного кроку ремонту (одна перевірка після правок замість 3 викликів моделі) і виміряти на 3+ прогонах — критерій: visual passed без зростання часу. Однієї вибірки для рішення замало.
2. **Час до першої дії при створенні сайту (~57–65 с до старту агента):** закешувати встановлений шаблон Next.js (node_modules) у sandbox, щоб не встановлювати його на кожне створення.
3. **Аналіз зовнішнього сайту:** маршрутизувати «проаналізуй <URL>» у Coding Agent з read-only набором і `code.web.fetch`, щоб аналіз базувався на реальній сторінці, а не на знаннях моделі.
