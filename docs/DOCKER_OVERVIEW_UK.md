# Як зараз працює Docker у NPATI Agent

Оновлено 09.10.2026 після впровадження спільного runtime для OSS / self-hosted.

**Основних контейнерів — 12. Новий магазин, блог або застосунок не додає Docker-контейнери: його файли та процеси працюють у спільному `npati-project-runtime`.**

| Контейнер | Функція |
|---|---|
| `npati-agent-web` | Чат, налаштування, редактор і сторінка Preview. |
| `npati-agent-api` | Авторизація, проєкти, файли, інструменти агентів, Data Studio, координація build/Preview. |
| `npati-agent-company-worker` | Фонові завдання агентів компаній. |
| `npati-agent-omniroute` | З’єднання з підключеними моделями та AI-провайдерами. |
| `npati-project-runtime` | Усі managed-проєкти: залежності, команди, build, tests і процеси Preview. Замінив локальний `npati-agent-sandbox-runner`. |
| `npati-agent-postgres` | Основна база платформи: компанії, проєкти, запуски та налаштування. |
| `npati-agent-postgres-projects` | Бази dev/prod і таблиці сайтів/застосунків. Спільний PostgreSQL; нова база не означає новий контейнер. |
| `npati-agent-redis` | Черги, координація та кеш. |
| `npati-agent-qdrant` | Векторний пошук і пам’ять агентів. |
| `npati-agent-minio` | Об’єктне сховище файлів і завантажень. |
| `npati-agent-crawler` | Читання зовнішніх вебсторінок. |
| `npati-agent-browser-use-worker` | Завдання агента у браузері. |

```text
npati-project-runtime — один Docker-контейнер
├─ /projects/<магазин-projectId>    → Next.js, власний процес і порт
├─ /projects/<блог-projectId>       → Next.js/Vite, власний процес і порт
├─ /projects/<застосунок-projectId> → Expo Web, власний процес і порт
└─ /projects/<api-projectId>        → Node.js, власний процес і порт
```

Порти призначаються автоматично, починаючи з 3001. Стандартний порт Next.js або Expo не резервується для кожного проєкту: система вибирає унікальний порт і передає його серверу. Node.js-проєкти мають слухати `process.env.PORT`.

1. Чат створює проєкт; агент генерує файли через наявні інструменти.
2. Постійні вихідні файли зберігаються через наявний WorkspaceProvider на томі API.
3. Runtime отримує робочу копію у `/projects/<projectId>`. Залежності й кеш зберігаються на його постійному томі.
4. Build, tests і Preview запускаються як окремі процеси цього проєкту. Нових sandbox/proxy-контейнерів немає.
5. Preview йде через web → API → runtime → порт вибраного проєкту.
6. Coding Agent працює з вибраним `projectId`; зміни повертаються через перевірку revision. Доступ, approvals і Activity залишаються в наявних API-сервісах.

В образі runtime вже є Node, npm/pnpm/yarn, Python і Git, а також підготовлені набори залежностей Next.js, Vite/React, Vite/Vue, Nuxt, Astro та Expo Web. Для сумісного стандартного `package.json` команда `npm install` отримує власну копію готових `node_modules` і lockfile без завантаження з npm. Наявний інший lockfile, додаткові залежності, інші версії чи install-скрипти використовують звичайний npm. Підготовлені набори спільні лише для читання; робочі залежності кожного проєкту окремі. Оптимізація не пропускає production build і не прискорює саму AI-модель.

Проєкти мають окремі Linux UID, env і логи. Landlock обмежує доступ процесу його каталогом та портом; спільний proxy і firewall контролюють вихід в інтернет. Перемикання проєкту проходить перевірки доступу. Restart/stop одного проєкту не зупиняє інші.

| Активні managed-проєкти | Основних контейнерів |
|---|---:|
| Без проєктів | 12 |
| Магазин | 12 |
| Магазин + блог | 12 |
| Магазин + блог + мобільний застосунок | 12 |

Це схема з увімкненим Data Studio, без сторонніх і старих контейнерів. Проєкти додають навантаження на CPU/RAM спільного runtime, навіть коли кількість контейнерів не змінюється.

Для безпечного спільного режиму потрібен Linux із Landlock ABI ≥ 6, зазвичай ядро 6.12+. На старішому сервері запуск відмовить; можна використати збережену ізольовану схему. Загальні ліміти runtime: `NPATI_PROJECT_RUNTIME_CPU` і `NPATI_PROJECT_RUNTIME_MEMORY`. Окремих Docker-лімітів RAM/CPU для кожного проєкту тут немає.

Попередню схему з `npati-sb-*` + `npati-proxy-*` збережено в `docker-compose.sandbox-isolated.yml` і `docker-compose.dokploy-isolated.yml` для ізольованого режиму. Старі контейнери автоматично не видаляються. Спільний режим не підтримує довільні host-folder mounts; для них потрібна ізольована схема.

Expo Preview показує вебверсію застосунку; це не публікація у магазинах застосунків. Live Preview залишається середовищем розробки. Після перезапуску API або runtime його потрібно запустити повторно.
