# Concurrent development in chat

Ordinary creation requests for websites, blogs, shops, CRM and mobile apps start up to four independent projects inside the one shared Sandbox runtime. A shop described as a website remains one project. Follow-up page/component edits and build-only requests stay on the existing chat path. Company and Sandbox modes use this flow; Global remains the mounted NPATI source workspace.

The installation uses one shared Sandbox container, following [the existing shared runtime decision](../website-builder/SHARED_PROJECT_RUNTIME.md). Each project has its own `/projects/<projectId>` working directory, Linux UID, process records and Preview port within that runtime. The chat flow reuses the configured provider; a logical `sandboxId` identifies a project workspace, not an additional container. Stopping a development task affects its own session and processes; hiding a tile preserves its project and does not stop the shared Sandbox.

The chat receives an immediate persisted acknowledgement. The API owns each background task, so closing the browser does not cancel development. The panel above the composer shows two tiles per row on desktop, at most four tiles. The narrow mobile layout keeps two columns with compact controls. Each project has its own existing Code session, files and development conversation. The production executor supplies the configured model, policy checks, verification and Live Preview.

Production build verification must pass before a tile becomes Ready. Expo mobile projects have a build script for web export, and Live Preview is that web export. Native device/store distribution is separate.

Click a tile or its pencil to open its project chat. Its leading back arrow returns to the parent chat. Stop explicitly cancels that task/session; it does not stop the other projects. Hide only updates the panel preference, preserves the project in Websites and does not cancel its run. Websites' existing Edit in chat link recovers the dedicated conversation if it was deleted. Asking to show all development processes restores up to four recent processes into one parent chat. Existing Websites projects from before this feature are adopted into the panel without being recreated or redeployed.

Bindings use authenticated user settings with revision checks, bounded to 128 records. Projects remain canonical ProjectService records, so Websites needs no separate project list. Each project has a persisted project card to route later chat changes to the correct project. Retry identities prevent duplicate projects after a lost acknowledgement. Existing API authentication, company ownership, write permissions, feature flags and execution scope are checked on the server.

The existing CodeRunAdmission queue and background registry are reused. The default per-user concurrency is now four; per-company concurrency remains five. An explicit NPATI_CODE_RUN_MAX_CONCURRENT_PER_USER environment value still takes precedence: installations configured to 2 will queue additional projects until the operator changes it. No new Docker service is introduced.

Run control retains the existing process-local cancellation limitation: use API affinity for multiple replicas. Durable Code run states report interrupted/finished sessions after a restart. Orphaned pre-session setup is reported interrupted after five minutes; it is not silently restarted. Interrupted or stopped projects remain editable through their project chat.

Validation: HTTP/service integration tests exercise real authenticated storage, admission, cancellation and the session executor with a controlled model port. They cover four concurrent projects, isolated failure and stop, lower configured limits, retry deduplication, preservation on hide, deleted-chat recovery and tenant/write permissions. Web rendering tests cover tile limits, back navigation controls, spinner states and escaping. These tests do not certify a production model/sandbox connection or deploy the changes.

## Deployment progress correction

Template deployment now uses the existing ProjectPreviewService.buildProject and startPreview before the first model call. Dependency install, template build, HTTP-ready preview and subsequent AI implementation are separate recorded stages in the project conversation. A template preview never means the requested AI edits have finished. The first implementation is bounded to 16 model turns (or a lower configured runner limit); quota limits are preserved. Prompts reference the actual code.deps.add tool instead of the nonexistent code.deps.install tool.

Each process owns one persisted project card, updated in place; card status comes from the run outcome, not the default Project.ready state. Existing duplicate placeholders/cards are suppressed when rendering, preserving substantive messages and project records. The main conversation contains the acknowledgement and process tiles; the project conversation contains the animated activity dot, deployment stages and actual tool activity. Regression tests cover quota exhaustion, no-model startup on template build failure, accurate card status, deduplication and the absence of project progress in the parent chat.
