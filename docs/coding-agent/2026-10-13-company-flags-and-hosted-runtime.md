# Coding Agent: права компанії та фактичний режим ai.npati.com

Дата: 2026-10-13.

## Перевірений сервер

Публічні GET-запити до https://ai.npati.com/api/health і /api/health/live повернули HTTP 200.
Основні сервіси повідомили про готовність. Це не є доказом успішної генерації через AI-модель.

GET /api/auth/installation/status повернув deploymentType: npati_hosted.
У цьому режимі self-hosted defaults і прив'язка власника інсталяції не застосовуються.
Значення connected: false в анонімному запиті стосується сесії браузера; воно не доводить,
що авторизований користувач не підключений.

## Знайдені дефекти і виправлення

1. Створення компанії не записувало її creator у company_members. Тепер обидва stores
   записують реальну роль owner. Повторне створення не змінює наявні ролі.
   Міграція 090 відновлює creator лише в компаніях, де взагалі немає записів членства;
   існуючі ролі, призупинення й рішення адміністратора залишаються чинними.
2. Керування flags перевіряло лише адміністративні маркери загального AuthContext.
   Тепер active owner/admin компанії може змінювати її flags і company kill switch.
   Global/user scope потребує попередніх адміністративних прав; business:manage сам собою їх не дає.
   API keys, remote tokens, agent/service identities не отримують права керування.
3. Company internal flags оцінюються з урахуванням записаної ролі компанії також у чаті,
   без підміни користувацького AuthContext глобальним адміністратором.
   Cache keys розрізняють тип авторизації та набір дозволів.
4. API повідомляє доступні області керування. UI вибирає Company для користувача без
   Global-доступу і блокує недоступні перемикачі.
5. Kill switch UI передавав companyId, якого schema не приймала. Тепер він передає scope.

Hosted defaults, rollout gates і пріоритет глобального master kill switch збережено.
Саме виправлення прав не вмикає всі flags без явного рішення користувача.

## Як підключається агент у чаті

Актуальний chat-stream-routes.ts має гілку створення сайта через Code:
CREATE_WEBSITE/CREATE_PROJECT + обрана компанія + увімкнений master ->
code_project -> prepareCodingWebsite -> toolchain -> session -> code_runner.
Для наступних повідомлень використовуються збережений project/session і картка розмови.
Preview відкривається після підтвердженої перевірки build; HTML/CSS не потребує вигаданого build.

При вимкненому master ця гілка не виконується. Запит може потрапити до попереднього
Website Builder/Company runtime, тому сама відповідь у чаті не доводить запуск Code.

## Межі перевірки

Авторизованого доступу до сервера, PostgreSQL і підключеної моделі ai.npati.com у цій сесії немає.
Локальний Docker daemon недоступний. На production нічого не змінено.

Перевірки прав і створення проєкту виконані через справжні API handlers та in-memory store.
Перевірки маршрутизації сайта використовують тестові порти. Існуючий app integration test
підтверджує code_runner та повторне використання сесії, але відхиляє run з audit_unavailable
в in-memory конфігурації. Це не є завершеним запуском моделі або live Preview.

До live-перевірки потрібні розгортання виправлення, перевірка режиму інсталяції й авторизований
запуск невеликого тестового сайта з перевіркою збережених файлів, build та HTTP Preview.
