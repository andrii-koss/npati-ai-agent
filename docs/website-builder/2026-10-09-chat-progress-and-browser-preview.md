# Етапи роботи в чаті, DSML і перевірка кнопки Preview

Локальна перевірка 09.10.2026.

## Виправлення

Раніше інтерфейс застосовував загальний індикатор змін компанії до запиту на створення сайту. Оркестратор не надсилав етапи виконання в SSE, тому користувач бачив «Company settings» протягом усього запуску.

Тепер чат отримує реальні події `project_progress`: підготовка проєкту, створення файлів, база й авторизація, робота агента, залежності, production build, запуск/перевірка Preview і завершення. Перед стартом сервера UI одразу показує підготовку запиту. Кожен етап має свою SVG-іконку, активну червону крапку та попередню анімацію тексту. Завершені етапи позначені галочкою; помилки — окремим станом. Файлові виклики можуть показувати шлях файлу, коли він присутній у параметрах виконуваного інструмента. Зміст файлів, команд, env і credentials у ці події не передається.

Підсумкова відповідь моделі іноді містила службові DSML-виклики замість текстового результату. Оркестратор більше не повертає цей протокол у повідомленні про проєкт: результат береться з виконаного шляху створення/build. Для редагування таке повідомлення описує збережену версію, не стверджує, що запропоновані службовим текстом зміни виконано. Frontend також приховує DSML у раніше збережених повідомленнях. Службовий текст не виконується як додаткові інструменти в обхід дозволів.

Стани approvals збережено: очікування погодження не позначається як готовий проєкт. Основний та multi-agent шляхи build/Preview передають події етапів через існуючий потік.

## Preview

Після перезапуску API його список активних Preview зникає, але процес у runtime може залишитися. Під час нового старту перевіряється журнал цього проєкту й зупиняється його раніше записаний Preview-процес із відповідною командою. Це запобігає конфлікту порту зі старим сервером. Інші проєкти не зупиняються. Порівняння також підтримує хешовані записи команд, які раніше вимагали approval.

Перед видачею нового підписаного Preview token перевіряється доступ до проєкту. Тест підтверджує, що інший користувач не отримує token чужого проєкту.

Для повідомленого запуску `0578963c-f50c-4c0b-a7d1-100512bf7d38` перевірено його справжній проєкт `61c39e58-2049-4a76-8214-55084be40a3c`. Його `app/page.tsx` відкриває `ProjectStore`, авторизація є окремою сторінкою `/auth`. Натискання саме кнопки Preview у браузері показало магазин із тестовим товаром. Початковий показ лише авторизації у цьому локальному стані не відтворився; не стверджуємо, що всі можливі причини такого показу усунено. Перевірені переходи на сторінку входу та назад залишаються всередині Preview.

## Повна перевірка через браузер

Chrome/Playwright відкрив `localhost:3000/chat` під сесією власника інсталяції, ввів і надіслав:

> Створи тестовий сайт інтернет магазин на Next.js, запусти build і Live Preview

Використано налаштовану живу модель та фактичний runtime, не mock відповіді:

- усі вісім етапів отримано через SSE й показано в DOM;
- спостерігалася анімована червона крапка `research-dot-pulse`;
- посилання «Company settings» у прогресі не з'являлося;
- підсумкова відповідь не містила DSML;
- production build успішний;
- натискання кнопки Preview відкрило магазин і тестовий товар;
- натискання «Вхід / Реєстрація» відкрило особистий кабінет сайту, а «На головну» повернуло магазин;
- після останнього оновлення API повторна перевірка цієї кнопки для нового проєкту також пройшла.

Час браузерного сценарію включає переходи на сторінку входу й назад, тому його не слід прямо порівнювати з попереднім виміром лише до першого Preview.

90 релевантних тестів пройшли, typecheck API/web та lint пройшли. Під час одночасних Docker build і браузерної перевірки два старі integration-тести перевищили свій 10-секундний timeout; повторний запуск без цього навантаження з одним worker пройшов, без збільшення timeout.

Локально оновлено `web`, `agent-api`, `company-worker`; runtime та дані проєктів збережені. Основних контейнерів залишається 12.

## Як повторити браузерну перевірку

Скрипт створює один постійний тестовий магазин під власником локальної інсталяції та використовує його підключену модель. Сесійні credentials і підписані URL не друкуються.

```powershell
npm install --prefix artifacts/browser-check --no-save --package-lock=false playwright-core
node scripts/verify-chat-browser.cjs
```

На Windows використовується встановлений Chrome. Для іншого шляху/ОС задайте `NPATI_BROWSER_EXECUTABLE` із шляхом до браузера. Потрібні запущені локальні Docker-сервіси та авторизована інсталяція.
