# Підготовлений runtime: реалізація та реальна перевірка

Перевірено локально 09.10.2026 у Docker Desktop.

## Що змінено

- Один `npati-project-runtime` містить Node/npm/pnpm/yarn, Python/Git і встановлені набори залежностей Next.js, Vite/React, Vite/Vue, Nuxt, Astro та Expo Web.
- Встановлення відбувається під час збирання образу. Для стандартних manifests `npm install` використовує власну копію готових залежностей у workspace проєкту, без повторного завантаження з registry. Каталог наборів захищений від запису процесами проєктів.
- Явний інший lockfile, версії, залежності, workspace/override або install lifecycle зберігають звичайний шлях npm. Оптимізація не підміняє довільні залежності користувача.
- Великі залежності винесено в окремий кешований Docker stage; зміни API не перевстановлюють усі фреймворки.
- Підсумкова відповідь моделі для проєкту отримує інструкцію коротко описувати перевірені результати, включно з етапом перевірки Company Knowledge. Це інструкція моделі, а не жорсткий ліміт токенів.
- Preview перевіряє реальний HTTP endpoint перед повідомленням про готовність. Тимчасові помилки під час запуску/першої компіляції повторюються; процес, який не запустився, зупиняється.
- Артефакти Nuxt/Astro та кеші виключено із синхронізації вихідних файлів.

## Створення магазину через чат

Використано сесію власника локальної інсталяції, його налаштовану модель і справжній маршрут `web → /api/chat/stream`. Запит:

> Створи тестовий сайт інтернет магазин на Next.js, запусти build і Live Preview

| Етап | Попередня перевірка | Після оптимізації |
|---|---:|---:|
| До відкритого Next.js Preview | 156 с | **99 с** |
| Підготовка залежностей | 38,7 с | **8,7 с** |
| Production build | 47,4 с | **45,3 с** |

Запуск агента в останній перевірці тривав приблизно 24 секунди. Решта часу включає підготовку проєкту/бази та запуск і перевірку HTTP Preview. Це окремі виміряні запуски, а не гарантія постійного часу: швидкість моделі, CPU, диск, джерельний код і нестандартні залежності впливають на результат. Підготовлені залежності прискорюють встановлення; вони не усувають генерацію коду та build.

Результат: `build=success`, production-build event `exitCode=0`, **перший** запит через web Preview proxy — `HTTP 200`, відповідь містить Next.js HTML. Попередню помилку передчасної готовності, коли перший запит отримував 502, відтворено та виправлено перевіркою HTTP readiness.

Тестовий проєкт залишено для перегляду: `eb4dbb2d-dfee-40fd-832f-e4c3a7569fcf`.

## Перевірка всіх підготовлених наборів

Скрипт `scripts/verify-prepared-project-runtime.cjs` виконав справжні build і перевірив шість одночасних Preview на різних портах:

| Набір | Підготовка залежностей | Build | Preview |
|---|---:|---:|---|
| Next.js | 8,9 с | 27,0 с | HTTP 200 |
| Vite/React | 1,1 с | 2,9 с | HTTP 200 |
| Vite/Vue | 0,5 с | 2,1 с | HTTP 200 |
| Nuxt | 5,7 с | 13,9 с | HTTP 200 |
| Astro | 5,4 с | 9,0 с | HTTP 200 |
| Expo Web | 22,5 с | 33,2 с | HTTP 200 |

Це мінімальні діагностичні проєкти, тому їхні build не слід порівнювати з повним магазином. Expo перевірено як експортовану вебверсію; це не native build для телефона.

Nuxt 4 у спільному однопортовому середовищі перевірено з `experimental: { viteEnvironmentApi: true }` у `nuxt.config.ts`. Його стандартний окремий SSR/HMR сервер вимагає додаткового випадкового порту та блокується ізоляцією. Конфігурація наявних проєктів автоматично не переписується; альтернативою є запуск зібраного `.output/server/index.mjs` на виділеному `PORT`.

## Захист і локальний стан

- Реальна діагностика підтвердила окремі env/логи, порти, зупинку/перезапуск у межах проєкту, блокування чужих файлів, symlink traversal, чужих портів, прямого виходу в мережу та DNS в обхід proxy.
- 67 релевантних тестів пройшли: prepared dependencies, shared runtime, Preview/readiness, company runtime і terminal integration. Typecheck API та lint пройшли. Повний набір усіх тестів репозиторію цим звітом не засвідчується.
- Локально оновлено runtime, API і company worker. **12 запущених контейнерів, усі healthy; 12 Docker images.** Нових контейнерів для діагностичних проєктів або магазину не створено.
- Діагностичні workspace прибрано скриптами; контрольний магазин збережено. Дані користувача та Docker volumes не видалялися.
- Образ став більшим; перше збирання встановлює всі набори один раз. Новий запит у чаті повторно цей образ не збирає.

Повторювана перевірка справжнього чату: `scripts/verify-chat-website.cjs`. Вона створює один постійний тестовий магазин, перевіряє build event і перший HTTP запит до Preview, не друкує credentials чи підписані URL. [Технічні деталі](SHARED_PROJECT_RUNTIME.md).
